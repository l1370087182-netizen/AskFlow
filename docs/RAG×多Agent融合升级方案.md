## 一、背景：两个项目互补

| | 本项目（RAG 学习系统） | AGENT 项目 |
|---|---|---|
| **知识能力** | ✅ 完整：爬取→切块→向量化（Milvus）→混合检索（BM25+向量+RRF+Rerank）→双协议流式生成 | ❌ 无向量库，"检索"靠实时联网搜索+网页抓取 |
| **编排能力** | ❌ 各功能手工编排（爬取队列、AI 添加、评估各写一套） | ✅ 黑板模式 + 任务板，13 个 Agent 协同，零直接通信 |
| **可靠性机制** | ⚠️ 有雏形（心跳、中断恢复），但任务状态全在 Redis | ✅ CAS 幂等写回、超时回收、强制 work_log、存储层状态机 |
| **鉴权/隔离** | ✅ JWT + 按用户隔离全套 | ❌ 零鉴权（演示系统，user_id 前端传参） |
| **工程形态** | 同步 FastAPI + MySQL + Redis + 线程 | 异步单进程 + SQLite(WAL) + asyncio + Redis Pub/Sub |
| **测试** | 临时验证脚本 | 确定性 Mock + 全系统夹具，无网络无真实 LLM 必须跑通 |

**结论：AGENT 有我们缺的「任务编排引擎」，我们有 AGENT 缺的「知识引擎」。**
融合后独有价值：**知识库成为中心资产，Agent 既消费它（检索回答）也生产它（爬取-质检-入库）**——这是任何单项目做不到的闭环。

## 二、AGENT 项目核心机制速览（借鉴依据）

### 2.1 黑板模式（第一代）

- **铁律**：Agent 之间禁止直接通信，只读写黑板；黑板是唯一真相源
- **统一工作项**：15 字段（id/type/status/tags/assignee/version/retry_count/trace_id/user_id/payload/output/work_log/dependencies/parent_id/claimed_at）
- **标签路由**：`tags` 是任务分发与认领的唯一依据；上游写回时换标签 → 事件总线按标签频道唤醒下游
- **两层锁认领**：Redis `SETNX ex=30s` + DB CAS（`WHERE status='pending' AND version=预期值`），Lua 比对后释放
- **幂等写回**：`WHERE id AND version AND assignee=self`，冲突放弃——防超时回收后原处理者迟到覆盖
- **状态机在存储层强制**：`pending → in_progress → completed/failed/revision_needed`，非法流转抛异常
- **事件驱动 + 心跳兜底**：Redis Pub/Sub 按标签频道唤醒，30s 轮询兜底防丢事件
- **无中央调度**：每个 Agent 独立循环，「下一个执行谁」由标签归属 + 先来先出 + 认领竞争涌现
- **超时回收器（TimeoutReaper）**：300s 无心跳 → 重置 pending（retry+1）；重试 3 次耗尽 → failed 并跳过，流水线不挂死
- **审核-修订闭环**：独立审核 Agent 三维度反向校验，≤3 轮，超限升级人工
- **强制 work_log**：每条含 agent_id/action/description/modified_fields（字段路径级）/bug_check/timestamp，存储层拒绝无日志写回

### 2.2 任务板模式（第二代，其 .env 当前主模式）

相对旧流水线的理念转变（它自己踩坑后演进的，直接借鉴可跳坑）：

| 旧流水线 | 任务板 |
|---|---|
| 发布→自动执行 | **发布≠执行**：钉板上（pinned），用户点「开始任务」才唤醒 |
| 标签巡检自动认领 | 按**能力注册表**（CAPABILITIES: kind→agent_types）自检接取 |
| 意图 Agent 直接派发 | 只写 `intent_note`+`intent_tags` 参考标记，不派发 |
| 审核/产出内置 | **一切皆任务**：做不完的环节发布子任务（`parents` 显式派发边） |
| 无交流边界 | 只有接取同一任务的 Agent 与发布用户能在该任务通道交流（存储层校验） |

收敛设计六点：单一 `task` 类型+`kind` 字段、任务通道独立表+权限校验、`parents` 显式派发边、触发收敛（仅「开始任务」发事件）、能力注册表、trace_id 泳道。

### 2.3 工程亮点

- **LLM 服务**：任务分级路由（TASK_TIER：规划/审核/答疑用大模型，摘要/意图/格式化用小模型）；结构化输出 = Schema 约束 + 宽容 JSON 解析 + 校验重试≤3；`MockLLMService` 确定性输出；`LLMProxy` 运行期热切换
- **对话即投影**：对话表只是黑板的追加日志+只读投影，幂等靠 `UNIQUE(item_id, version, kind)`；Agent 永不读对话表
- **数据库是唯一真相源**（铁律 9）：Redis 只做锁/缓存/事件，启动从 DB 重建
- **测试纪律**：`fakeredis` 离线可跑、`ASGITransport` 全系统夹具、`poll_until` 异步收敛轮询

## 三、目标架构

```text
                  ┌────────────── 学习任务板（用户发布学习目标）──────────────┐
                  ▼                                                          │
 学习规划 Agent ─（意图打标+缺口拆解）─▶ 缺口×N ─┬─▶ 知识库检索（混合检索作工具）─▶ 学习材料
                                               └─▶ 缺失 → 生产 Agent 爬取 → 质检 Agent 审核 → 入库
 知识生产流水线（任务引擎，后台异步）：
   生产 Agent（爬取+清洗，N 实例并行）→【质检 Agent：规则优先+LLM 复核，≤2 轮】
   → 向量化（工具步骤，非 Agent）→ 整理 Agent（术语注册 tech_term）
 对话链路（同步编排，不进任务引擎）：
   检索编排器（查询改写 → 混合检索 → 结果评审 ≤2 轮重检）→ 生成（现有链路）→ 引用核查（提示词侧）
 学习闭环：
   费曼评分 / 模拟面试结果 → 学习规划 Agent → 弱项推卡片 / 拆解学习任务钉板 → 计划迭代
   复测面试（同一 JD）→ 客观验证任务成效 → 进阶/补救任务（见 §五·阶段 2 面试联动）
```

**中心思想**：知识库是唯一真相资产；任务引擎（agent_task 表 + 黑板机制）是**后台** Agent 的地基；
对话侧编排是同步函数组合（不进任务引擎，不牺牲延迟）；后台生产/质检/规划走任务引擎（可并行、可恢复、可审计）。

## 四、Agent 角色清单（收敛版：4 个后台角色 + 1 个同步编排器）

### 4.1 准入原则——什么才配当「Agent」

一个环节做成独立 Agent（进任务引擎、可认领/可恢复），必须至少满足一条：

1. **需要并行**：多实例分摊工作（如多站点同时爬取）
2. **需要后台生命周期**：耗时长、可断点续跑、需超时回收/重试
3. **职责分离**：审核者不能是生产者自己（防自审自过）

**不满足的环节一律做成「工具步骤」**（流水线内联调用或同步函数），
强行 Agent 化只增加任务交接、状态表和延迟，不带来任何收益。

### 4.2 角色清单

**A. 对话侧——同步编排器（不进任务引擎，请求内完成）**

| 角色 | 职责 | 模型档位 | 说明 |
|---|---|---|---|
| **检索编排器** `RetrievalOrchestrator` | ① 查询改写/拆解（多查询）+ 分类过滤建议 ② 检索结果相关性评审，不够则换策略重检，**≤2 轮** | 小模型 | 一个类两个提示词，非驻留 Agent——对话是同步交互，走任务认领只会加延迟、不带来并行；延迟预算 3-5s，超时直接放行原始检索结果 |

**B. 后台侧——任务引擎 Agent（4 角色）**

| 角色 | 职责 | 实例数 | 模型档位 | 状态 |
|---|---|---|---|---|
| **生产** `producer` | 整站爬取 + AI 清洗（逐页容错、心跳、中断恢复） | **N=3 并行** | 用户个人模型 | ✅ 已有（现爬取设施），迁入任务引擎即可 |
| **质检** `reviewer` | ① 单篇内容质检：拒答回退/导航页残留/乱码/与分类无关——**规则优先，规则拿不准才调 LLM** ② 整批爬完的汇总复核 | 1 | 小模型 | 🆕 阶段 1 |
| **整理** `curator` | 术语提炼注册 `tech_term`（批量、懒触发：攒 N 篇或用户进卡片页时按需补）、条目简介生成 | 1 | 小模型 | 🆕 阶段 1 后段 |
| **学习规划** `planner` | ① 费曼评分→弱项定位→推卡片/触发补充爬取 ② 面试结果→结构化弱项→拆解学习任务 ③ （阶段 2）学习目标意图打标+缺口拆解+材料编排 | 1 | 大模型（低频） | 🆕 阶段 1③ 起 |

### 4.3 为什么这样收敛（对照原方案的删改）

| 原方案角色 | 处置 | 理由 |
|---|---|---|
| 爬取 Agent + 清洗 Agent | **合并**为 `producer` | 同一逐页流程，拆开只增加任务交接成本，无并行/分离收益 |
| 入库/向量化 Agent | **降级为工具步骤** | 机械操作无 LLM，向量化始终内联在生产流程里（现状即如此） |
| 查询规划 Agent + 检索评审 Agent | **合并**为同步 `RetrievalOrchestrator` | 对话内毫秒级衔接的两步，做成两个异步 Agent 会增加秒级任务交接延迟，且对话链路无并行需求 |
| 生成 Agent | **取消** | 现有 `ChainBuilder` + 流式生成已是该角色，无需包装 |
| 引用核查 Agent | **降级为提示词约束** | 要求回答标注片段编号即可；真做独立核查调用，成本高收益低，后续有需要再升级 |
| 意图 Agent（阶段 2） | **并入** `planner` 入口 | 意图打标只是规划的第一步，AGENT 项目自己也收敛到"意图只打标不派发"，一个函数即可 |
| 术语 Agent + 条目整理 | **合并**为 `curator` | 同为"已有知识的整理"，时机相近 |
| 学习闭环规划 + 任务板规划 | **合并**为 `planner` | 同为"依据用户状态/目标产出学习计划" |

**一句话**：角色从 ~10 个收敛到 **4+1**——唯一强制独立的是质检（审核与生产必须分离），
唯一强制多实例的是生产（并行收益），其余按"有没有并行/后台/分离需求"逐个检验。

### 4.4 成本与触发控制

- **规则优先**：质检先用零成本规则（长度、围栏占比、模板词、分类关键词命中率），只有规则拿不准的才花一次小模型调用
- **懒触发**：`curator` 不做常驻巡检，攒批或按需触发，避免空转调用
- **小模型专用位**：`planner` 之外的 Agent 环节全走小模型；用户个人模型只承担生成与清洗（面向用户可见的产出）
- **轮数上限**：质检 ≤2 轮、检索重检 ≤2 轮，超限放行并记 work_log，永不挂死

## 五、分阶段实施

### 阶段 0：地基——通用任务引擎（最优先）

现状：爬取任务设施（队列 + inflight 集合 + 心跳 + 恢复）是手搓任务引擎，
缺 AGENT 验证过的四件套，且状态全在 Redis（重启失忆）。

1. **建 `agent_task` 表**（MySQL，真相源），精简版黑板字段：
   ```
   id / kind / status / tags(JSON) / assignee / version / retry_count
   / user_id / trace_id / payload(JSON) / output(JSON)
   / work_log(JSON) / parent_id / claimed_at / created_at / updated_at
   ```
   - kind 枚举先行（只收后台异步任务；对话侧编排不进引擎）：`crawl`（现有爬取迁入）、`quality_review`、`term_curate`、`study_plan`、`learning_goal`……
   - `payload.source` 血缘约定：`{"type": "interview"|"goal"|"feynman", "id": ...}`，
     任务板卡片可回溯"为什么派这个任务"（面试驱动场景的关联基础）
   - 状态机白名单放存储层（DAO 拒绝非法流转）
2. **两层锁认领 + CAS 幂等写回**：替换现在单层 inflight 方案
3. **强制 work_log**：每次写回必附（agent/动作/字段级变更），无日志拒绝写入
4. **超时回收 + 重试上限 3 + 失败跳过**：统一到引擎（爬取现有心跳机制并入）
5. **Redis 降级为锁/事件层**：任务状态一律从 DB 读；启动自检从 DB 重建执行视图
6. **事件总线（可选跟进）**：Redis Pub/Sub 按 kind/tags 频道 + 轮询兜底，
   前端从 2s 轮询逐步换为事件推送（SSE，保持本项目风格，不引入 WS）

**迁移策略**：爬取任务第一个迁入（已有前端面板，契约基本不变）；跑稳后其他异步功能逐步收编。

### 阶段 1：按角色清单改造现有链路

#### 1① 编排检索——同步 `RetrievalOrchestrator`（对话质量直接提升，ROI 最高）

对话是同步交互，编排器**不进任务引擎**，就是 `chain.py` 前置的一段函数组合：

```
用户问题 → ① 查询改写/拆解（小模型，1 次调用）→ ② HybridRetriever 检索（现有，不动）
        → ③ 结果评审（小模型）：相关 → 进生成；不够 → 换策略重检（≤2 轮）
        → ④ 现有 ChainBuilder + 流式生成（提示词要求标注片段编号，兼做引用约束）
```

- 延迟预算 3-5s：任一步超时/失败 → 放行原始检索结果，对话永不因此变慢失败
- 讲解模式（问）全量启用；费曼模式选题检索沿用单次检索即可（无需编排）

#### 1② 知识生产流水线——`producer`（已有）+ `reviewer`（新增）+ `curator`（新增）

```
producer：爬取+清洗（已实现，迁入任务引擎）→ 向量化（工具步骤内联，非 Agent）
reviewer：quality_review 任务（规则优先，拿不准才调小模型）
curator：term_curate 任务（攒批懒触发）
```

- **质检 `reviewer`**（借鉴审核-修订闭环）：规则层先筛（正文长度、代码围栏占比、模板词、与分类关键词命中率），规则判不定的才花一次小模型；不过关 → 退回重洗或丢弃，≤2 轮；判定理由写 work_log
- **整理 `curator`**：批量提炼术语注册 `tech_term`，取代手工 `scripts/seed_terms.py`，每日卡片数据源自动增长；不做常驻巡检，攒 N 篇或按需触发；**只处理全局条目**——个人知识库内容不注册全局术语表（防个人学习内容泄漏）
- 一次爬取会话全程同一个 `trace_id`，前端面板可展示逐阶段进度

#### 1③ 学习闭环——`planner`（本项目特色，保留并强化）

- 费曼评分（已有）→ `planner` 的 `study_plan` 任务：弱项定位 → 推荐知识卡片（`GET /api/card/today` 扩展为按弱项推）/ 触发补充爬取
- 对应 AGENT 的「进度提交→判定→补救/进阶计划」闭环，数据源换成本项目独有的**评分记录 + 知识掌握画像**

#### 1④ 面试结果落库（任务板关联的前置，可独立先做）

现状短板：面试会话结束时 `save_session(..., {"messages": [], "meta": {}})` 直接清空，
**面试结果是一次性的**——总评、缺口、逐轮表现全部丢失，无法被任何下游消费。改造：

1. **新增 `interview_record` 表**：
   ```
   id / user_id / jd_id（复用现有 jd 表存 JD 分析，不重复建）
   / resume(JSON) / rounds / transcript(JSON，逐轮问答)
   / final_summary / weaknesses(JSON) / gap_topics(JSON) / created_at
   ```
2. **JD 分析复用 `jd` 表**（已有 user_id 隔离 + tech_stack 子表）：面试 `start` 时
   把 `jd_analysis` 落一条 jd 记录，`interview_record.jd_id` 指过去——同一份 JD
   的多次面试、多次 JD 分析天然归拢
3. **总评改结构化输出**：`FINAL_ASSESS_PROMPT` 要求模型额外输出
   `weaknesses: [{topic, evidence(引用答题原话), level}]` JSON，
   解析沿用 evaluate 模块的「正则优先 + LLM 兜底」模式——
   这是后续自动生成学习任务的**结构化原料**（自由文本总评没法精确映射任务）
4. 会话结束后数据不再清空；前端总评卡片下增加「查看本次面试记录」入口

### 阶段 2：学习任务板（产品形态）

移植 AGENT 第二代任务板（跳过它旧流水线的坑），规划侧全部由 `planner` 承担。
任务板有两条入口，**面试驱动是首选场景**：

#### 2A. 首选场景：面试驱动的学习任务（面试 × 任务板联动）

```
面试结束（1④ 已落库）
  → 总评页出「生成学习计划」按钮（发布≠执行，钉板不自动跑）
  → 用户点「开始任务」→ planner 消费 interview_record：
      输入 = JD 要求（jd.tech_stack）− 简历技能（resume.skills）= 客观缺口
            + weaknesses（答题证据级弱项）= 实测短板
      拆解规则：
        · 每个「弱项」(weakness) → 一个高优学习任务（有答题原话证据，最可信）
        · 每个「缺口但没考到」的 JD 要求 → 普通学习任务
        · 任务 payload.source = {"type": "interview", "id": 面试记录id}（血缘）
  → 每个学习任务：先查知识库（混合检索，范围 = 全局知识 + 本人个人知识，
    即现有检索传 uid 的行为）命中 → 编学习材料；
    缺失 → 自动发爬取子任务（复用 producer，**入库到本人个人知识库**，
    user_id=自己、source_type=personal，同现有「爬取整站」归属规则）
    → 质检通过后再编
  → 闭环验证：学完 → 复测面试（同一 JD）→ planner 对比两次面试的
    weaknesses/gap_topics → 生成进阶/补救任务（版本化不覆盖）
```

**数据归属与隔离（重要）**：
- 学习任务补料爬取的内容**只进个人知识库**，不混入全局语料（user_id=0）——
  每个用户的学习缺口不同，爬来的内容只对本人有学习价值
- 个人知识不注册全局术语表（`tech_term` 供每日卡片用，全局可见）——
  `curator` 只处理全局条目，防止个人学习内容泄漏给他人
- 面试记录、学习任务、任务通道全部按 `user_id` 隔离，越权读路 404，与现有约定一致

**这是本项目相对 AGENT 的独特优势**：AGENT 的学习进度靠用户**自报**
（`progress_submit`，进度 Agent 只能保守判定"无法证实一律按未完成"）；
本项目有模拟面试——**复测就是客观考试**，任务成效不靠自觉，靠分数说话。
面试记录里的 `evidence`（答题原话）还能在任务卡片上展示"为什么给你派这个任务"。

关联的双向可追溯：
- 面试记录页 → 「由本次面试生成的任务」列表（按 `payload.source` 反查）
- 任务板卡片 → 「来源：X 月 X 日面试 · 第 3 轮答错『Redis 持久化』」（`payload.source` 正查）
- 同 `trace_id` 串起：面试记录 → 学习任务 → 爬取子任务 → 复测记录（泳道展示）

#### 2B. 目标驱动：自由发布学习目标

1. 用户发布学习目标（如"掌握 FastAPI 依赖注入"）→ `planner` 入口做意图打标+缺口拆解（一个任务内完成，不单设意图 Agent）
2. 缺口原子化：一缺口一子任务，可并行
3. 每个缺口：**先查知识库**（混合检索，全局+本人个人），命中 → 直接编学习材料；缺失 → 自动发爬取子任务（入**本人个人知识库**，同 2A 归属规则）→ 质检通过后再编
4. 用户学完提交反馈 → 计划迭代（补救/进阶），版本化不覆盖

5. 前端可视化借鉴：Agent 活动气泡、trace 泳道、work_log 查看器、任务通道（接取者+用户可交流）

## 七、坑与取舍

1. **并发模型保持同步**：AGENT 是 asyncio 单进程（SQLite 约束），本项目是同步 FastAPI+MySQL+线程。
   黑板引擎用**同步 SQLAlchemy 重写**（逻辑照抄、IO 层换），Agent 跑线程。
   ❌ 不要为移植把项目改成 async，成本远大于收益
2. **鉴权不可照抄**：AGENT 零鉴权；本项目黑板/任务必须全带 `user_id` 隔离，读路隐藏存在性（404）与现有约定一致
3. **先做大小模型分级再上多 Agent**：评审/质检/意图都是新增调用，不分级成本翻倍；
   个人模型场景下：用户模型当大模型，服务端配置一个小模型专供 Agent 内部环节
4. **Milvus Lite 单进程独占**：多线程已加进程锁（现状）；将来要多进程部署 Agent，Milvus 必须换 standalone
5. **标签过滤下推数据库**：AGENT 在 Python 侧过滤（条目少），我们规模大，`tags` 查询走 SQL（JSON_CONTAINS 或关系表）
6. **对话链路延迟预算**：检索编排器必须小模型+轮数上限+超时放行，对话体验优先于检索完美；这也是它不进任务引擎的原因
7. **循序渐进**：阶段 0 + 1① 跑通即有巨大收益；阶段 2 是产品级改造，最后做
8. **会话文件的重构时机**：`sessions/{uid}/*.json` 是现状短板（难查询），但不急——阶段 2 随任务板一起改成 DB+投影，避免两遍工

## 八、建议的第一步（最小闭环）

> **建 `agent_task` 表 + 两层锁认领 + CAS 写回 + work_log，把现有爬取任务迁进去；
> 然后给对话链路加同步检索编排器（改写+评审一个类，小模型，超时放行）。**

完成后：任务引擎立住（后续所有 Agent 的地基）；用户立刻感受到回答质量变化（编排检索生效）；
全程不碰现有接口契约，前端几乎不改。此时系统里只有一个后台角色 `producer`（爬取，已有）+
一个同步编排器——增量最小，验证最快。

**可并行的独立小项**：1④ 面试结果落库——不依赖任务引擎，随时可做；
它是面试联动的前置，也是独立的用户价值（面试记录不再丢失）。
